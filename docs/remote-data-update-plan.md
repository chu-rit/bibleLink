# 원격 단어·맵 데이터 업데이트 계획

## 목표

앱을 실행할 때마다 최신 단어 데이터와 맵 데이터를 확인하고, 최신 데이터가 있으면 내려받아 적용한다. 인터넷에 연결되지 않았거나 업데이트에 실패한 경우에는 기기에 저장된 데이터로 계속 진행한다.

## 대상 플랫폼

- Web
- iOS
- Android

세 플랫폼 모두 별도 네이티브 모듈을 추가하지 않고 `fetch`와 기존 `AsyncStorage`를 사용한다.

## 데이터 제공 방식

GitHub Pages에서 정적 JSON 파일을 제공한다. 현재 웹 배포 주소와 같은 출처를 사용해 Web의 CORS 문제를 줄이고, iOS·Android에서도 HTTPS로 접근할 수 있게 한다.

예정 경로:

```text
https://chu-rit.github.io/bibleLink/data/manifest.json
https://chu-rit.github.io/bibleLink/data/words/bibleWordsLib1.json
https://chu-rit.github.io/bibleLink/data/maps/crosswordMaps.json
```

## 버전 확인

`manifest.json`을 추가하고 데이터 버전을 명시한다.

예시:

```json
{
  "version": "20260901.1",
  "words": "data/words/bibleWordsLib1.json",
  "maps": "data/maps/crosswordMaps.json"
}
```

앱은 manifest의 버전과 기기에 저장된 데이터 버전을 비교한다. 원격 버전이 더 최신일 때만 단어 데이터와 맵 데이터를 다운로드한다.

## 앱 시작 흐름

1. 로딩 화면을 표시한다.
2. 앱 번들에 포함된 기본 단어·맵 데이터를 초기 fallback으로 준비한다.
3. `AsyncStorage`에서 다음 캐시를 읽는다.
   - 캐시된 데이터 버전
   - 캐시된 단어 데이터
   - 캐시된 맵 데이터
4. 캐시가 유효하면 우선 캐시 데이터를 사용한다.
5. 인터넷 연결을 확인하고 원격 `manifest.json`을 요청한다.
6. 원격 버전이 더 최신이면 단어·맵 JSON을 다운로드한다.
7. 다운로드한 데이터의 기본 구조와 `wordId` 연결을 확인한다.
8. 검증에 성공하면 새 데이터를 `AsyncStorage`에 저장하고 현재 앱 데이터로 적용한다.
9. 최신 데이터이거나 인터넷이 없거나 다운로드에 실패하면 기존 캐시 데이터로 진행한다.
10. 캐시도 없으면 앱 번들에 포함된 기본 데이터로 진행한다.
11. 데이터 결정이 끝나고 폰트 로딩도 완료되면 로딩 화면을 닫고 기존 화면을 표시한다.

## 오프라인 fallback 우선순위

```text
최신 원격 데이터
  -> 저장된 캐시 데이터
  -> 앱 번들 기본 데이터
```

인터넷 연결 실패나 원격 데이터 오류 때문에 앱 사용을 막지 않는다. 단, 저장된 JSON이 손상되었거나 기본 구조가 맞지 않으면 해당 캐시를 버리고 다음 fallback으로 넘어간다.

## 로딩 화면

새 로딩 화면 컴포넌트를 추가하거나 기존 앱 구조에 최소한으로 반영한다.

표시 내용:

- Bible Link 로고 또는 앱 이름
- 데이터 확인 중 상태 문구
- 업데이트 중일 때 업데이트 상태 문구

데이터 업데이트가 느리더라도 사용자가 앱이 멈춘 것으로 오해하지 않도록 한다. 네트워크 요청에는 timeout을 둔다.

## 코드 변경 예정 범위

- `App.js`
  - 앱 시작 데이터 로딩 상태 관리
  - 로컬 캐시 읽기
  - manifest 및 최신 데이터 다운로드
  - fallback 처리
  - 로딩 화면 표시
  - 결정된 단어·맵 데이터를 하위 화면에 전달
- `screens/MapSelectScreen.js`
  - 정적 맵 import 대신 App에서 전달한 맵 데이터 사용
- `screens/WordSearchScreen.js`
  - 정적 단어·맵 import 대신 App에서 전달한 데이터 사용
- 데이터 로더 파일
  - 필요한 경우 원격 데이터 로딩과 검증 로직을 별도 파일로 분리
- `data/manifest.json`
  - 현재 데이터 버전과 원격 파일 정보 저장
- 배포 설정
  - GitHub Pages의 `dist`에 manifest, 단어 JSON, 맵 JSON 복사

새 의존성은 추가하지 않는다.

## 데이터 구조 결정 사항

현재 앱의 맵 데이터는 여러 개의 JSON 파일을 정적으로 import하고 있으므로, 원격 업데이트 시에는 앱에서 사용하는 맵 목록을 하나의 JSON으로 제공하는 방식을 우선 검토한다.

단어 데이터는 현재 병합 결과인 `bibleWordsLib1.json`을 사용한다. 원본 Lib2~Lib15는 관리용이며 앱 업데이트 파일은 Lib1 병합 결과를 배포한다.

## 검증

원격 데이터 적용 전에 최소한 다음을 검사한다.

- JSON 파싱 가능 여부
- 단어 데이터가 배열인지 여부
- 맵 데이터가 배열인지 여부
- 맵의 `wordId`가 단어 데이터의 `id`와 연결되는지 여부
- 맵의 기본 필드와 cells 구조 존재 여부

개발 및 데이터 변경 후:

- `npm run merge:lib1`
- `npm run validate:maps`
- JSON 유효성 확인
- Web, iOS, Android에서 최초 실행 및 오프라인 재실행 확인

`npm run build:web`은 구현 및 배포를 확인할 필요가 있을 때 실행한다.

## 예외 및 주의 사항

- 원격 데이터가 최신이어도 검증에 실패하면 기존 캐시를 유지한다.
- 캐시 저장 중 오류가 나도 현재 메모리의 정상 데이터로 앱을 계속 실행한다.
- 기존 퍼즐 진행 데이터의 키는 맵 `id`를 사용하므로 데이터 업데이트 시 기존 맵 `id`와 배치 관계를 함부로 변경하지 않는다.
- 맵을 제거하거나 ID를 변경하는 데이터 업데이트가 진행 데이터에 미치는 영향을 별도로 검토한다.
- GitHub Pages의 배포 지연과 브라우저·CDN 캐시를 고려해 버전 변경으로 최신 여부를 판단한다.

## 구현 전 확인이 필요한 사항

- manifest 버전 형식: 날짜 기반 문자열 또는 증가하는 숫자
- 원격 맵 데이터 파일을 하나로 합칠지, 개별 맵 JSON을 유지할지
- 업데이트 중 로딩 화면을 유지할 최대 시간
- 원격 업데이트 실패 시 사용자에게 간단한 안내 문구를 표시할지 여부
